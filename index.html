Event Loop

Один виток цикла

Простыми словами: браузер работает как один повар на кухне. Он готовит одно блюдо за раз, а между блюдами может выглянуть в зал. Заказы ждут в очередях, а цикл решает, что делать дальше.

Call stack — стопка функций, которые выполняются прямо сейчас. Пока стек не пуст, цикл ждёт.

  1. Взять одну macrotask и выполнить до конца.
  2. Выполнить все microtasks, включая те, что появились по ходу.
  3. Только если подошло время кадра: rAF → layout → paint → composite.

* Цикл идёт по кругу: 1 → 2 → 3 → 1 …

Если работа не укладывается в кадр, перерисовка кадра (пункт 3) пропускается, и анимация дёргается.

При 60 Гц на кадр есть 16,6 мс: перерисовка пропустится, если macro, одна micro или все micro в сумме идут дольше. Например, работа на 40 мс пропустит 2 кадра, в 16,67 и 33,33 мс, а новый кадр появится на экране в 50 мс.

Попадут ли задачи, созданные на лету, в этот же цикл?

Micro да, до перерисовки. Macro нет, она ждёт следующего витка.

Новая macro, например setTimeout из задачи, встаёт в очередь macro. Перед ней браузер может нарисовать кадр.

Новая micro выполнится на этом же шаге. Создать её может и macro, и другая micro.

Из macro: задача ставит microtask в очередь, а выполнится та, когда macro закончится и стек опустеет.

Из micro: пока идёт одна microtask, она может поставить ещё одну. Новая попадает в ту же очередь и выполнится на этом же шаге, до кадра и до следующей macro.

Поэтому мелкие micro могут затормозить кадр. Даже если они укладываются в кадр, одна из них может создать тяжёлую micro или длинную цепочку micro. Всё это выполнится до перерисовки: кадр задержится, а если работа займёт больше 16,6 мс, следующие кадры будут пропущены.

setTimeout(() => {                 // macro
  queueMicrotask(() => {           // micro 1: поставила macro
    queueMicrotask(() => {         // micro 2: поставила micro 1
      console.log("micro 2");
    });
    console.log("micro 1");
  });
  console.log("macro");
});
// Вывод: macro, micro 1, micro 2

Шаг 2 заканчивается, только когда очередь microtasks пуста. Похожий сценарий показан в панели «Стек и очереди».

Как часто вызывается rAF?

Раз в кадр: при 60 Гц каждые 16,67 мс (1000 ÷ 60).

Частоту задаёт экран: при 120 Гц будет 8,33 мс. Это не таймер, поэтому если главный поток занят, кадр пропускается и следующий вызов приходит позже.

Важная деталь: rAF срабатывает один раз. Чтобы анимация продолжалась, колбэк сам снова вызывает requestAnimationFrame. Несколько колбэков, поставленных до кадра, выполнятся все в этом кадре.

Успевает ли пройти несколько циклов между кадрами?

Да, если задачи короткие, витков может быть много. А может не быть ни одного полного кадра, если задача длинная.

Что блокирует перерисовку?

И macro, и micro. Браузер рисует, только когда главный поток свободен.

Что выполняетсяЗаблокирует на 40 мс?Почему
Одна macro на 40 мсДазадачу нельзя прервать посередине
Одна micro на 40 мсДапо той же причине
Много мелких micro, в сумме 40 мсДаочередь выполняется целиком, кадр не вклинится
Много мелких macro, в сумме 40 мсОбычно нетмежду ними браузер может нарисовать кадр
 
Мелкие micro:  [m][m][m][m][m][m][m][m] ... 40 мс подряд → кадр
Мелкие macro:  [M][M][M] кадр [M][M][M] кадр [M][M]

Работа занимает те же 40 мс, но мелкие macro дают браузеру рисовать между ними.

Поэтому разбивка тяжёлой работы на microtasks не помогает:

// Не помогает: кадр не вклинится, пока очередь не опустеет
for (const item of items) {
  queueMicrotask(() => process(item));
}

// Помогает: каждый setTimeout это отдельная macrotask
for (const item of items) {
  setTimeout(() => process(item));
}

С await то же самое: если промис уже выполнен, код после него продолжится как microtask, и паузы для отрисовки не будет.

Когда браузер рисует кадр

После каждого витка браузер проверяет, настало ли время кадра. Текущую задачу он никогда не прерывает.

Правила

  • Кадр: при 60 Гц его момент наступает каждые 16,67 мс по сигналу экрана.
  • Micro: идут вне очереди, все сразу после текущей macro.
  • Macro: строго по одной за виток.
  • Время кадра не настало: браузер может взять следующую macro.
  • Время кадра настало во время задачи: браузер ждёт конца macro и всех micro. Лимита на ожидание нет.
  • Менять на экране нечего: перерисовки может не быть.

Пример: кадр опоздал

0 мс      macro 1
10 мс     macro 2: время кадра не настало, значит можно
16,67 мс  момент кадра: macro 2 идёт, браузер ждёт
20 мс     macro 2 и micro закончились → перерисовка, опоздание 3,33 мс
22 мс     перерисовка закончилась (допустим, заняла 2 мс)
33,33 мс  следующий момент кадра

Опоздание не сдвигает следующие кадры. Следующий момент остаётся в 33,33 мс, поэтому на работу до него есть не 16,67 мс, а около 11 мс.

Пример: кадр пропущен

0 мс      старт задачи на 40 мс
16,67 мс  момент кадра, задача идёт
33,33 мс  ещё один момент кадра, задача идёт
40 мс     задача закончилась → браузер готовит один кадр
50 мс     ближайший сигнал экрана

Пропуск не решается заранее: за время задачи прошло несколько моментов кадра, а нарисовать можно только один, с актуальным состоянием. Браузер может подготовить кадр сразу после задачи или ближе к сигналу экрана, это зависит от браузера.

Почему куски macro не блокируют кадр

За один виток выполняется одна macro, поэтому новая macro из postMessage ждёт следующего витка, а перед ним браузер проверяет время кадра.

Виток 1: кусок macro 5 мс → все micro → кадр, если пора
Виток 2: кусок macro 5 мс → все micro → кадр, если пора

Ограничение: лимит 5 мс считает только код внутри куска. Micro выполнятся уже после него, и тяжёлые micro всё равно задержат кадр:

[кусок macro 5 мс] [micro 30 мс] → кадр задержался

Разбивка работает, только если короткие и macro, и все micro после неё.

Отменяется ли кадр, если он уже не актуален?

Отменять нечего: заранее кадр не считается.

Браузер считает кадр на шаге 3 и берёт DOM и стили такими, какие они в этот момент. Поэтому устаревшего кадра не бывает: рисуется последнее состояние.

Если DOM менялся несколько раз между кадрами, на экран попадёт только итог. Промежуточные значения никто не увидит.

Если кадр пропущен, он не встаёт в очередь и не догоняется. Следующий кадр просто покажет актуальное состояние, поэтому анимация выглядит как рывок.

Если отрисовка уже началась, она не прерывается: это такая же работа в главном потоке, и новые задачи ждут её конца.

Колбэк rAF при пропуске кадра не теряется: он выполнится один раз перед следующей отрисовкой.

Может ли сама отрисовка идти дольше кадра?

Да. Тогда следующий кадр пропускается, как и при длинной задаче.

Rendering в главном потоке (rAF, layout, paint) не прерывается. Пока он идёт, момент следующего кадра проходит впустую, а macro и micro ждут. Новая отрисовка не запустится поверх текущей: второй нет, пока не закончится первая.

0 мс      отрисовка началась (длится 25 мс)
16,67 мс  момент кадра пропущен
25 мс     отрисовка закончилась, идут задачи
33,33 мс  следующий кадр

Важные данные, пришедшие во время отрисовки, не теряются. Событие ждёт в очереди, затем записывает их в DOM, и ближайший кадр их покажет. Пропуск кадра означает задержку, а не потерю. Не увидеть можно только промежуточное значение, если до кадра его перезаписали новым. Этот сценарий есть в конце анимации.

Обычно это тяжёлые layout и paint: огромный DOM, чтение размеров вперемешку с записью в rAF, дорогие тени и фильтры.

Потоки и CSS-анимации

JS и подготовка кадра идут в главном потоке, а готовую картинку собирает отдельный поток-композитор.

Джуну: простыми словами

Анимация transform или opacity двигает уже нарисованный слой, как лист бумаги на столе. Анимация width каждый кадр заново вычисляет раскладку страницы. Первой главный поток обычно не нужен, второй нужен всегда.

Растеризацияпотоки растеризации, GPU
Compositeпоток композитора, GPU

background-color, box-shadowобычно Paintзамирает или дёргается
transform, opacityобычно только Compositeобычно продолжается
JS через requestAnimationFrameзависит от кодазамирает
 
.bad  { transition: left 0.3s; }        /* Layout каждый кадр */

Важно: крутящийся CSS-спиннер не доказывает, что интерфейс отзывчив. Спиннер может идти на композиторе, пока клики ждут в очереди.

Сеньору: что под капотом

  • Слои: браузер сам решает, что вынести на отдельный слой. will-change: transform подсказывает это заранее, но каждый слой расходует память.
  • Forced layout: чтение offsetHeight после записи стилей заставляет считать раскладку сразу. В цикле это даёт layout thrashing.
  • Прокрутка: часто идёт на композиторе, но не-passive обработчик touchstart или wheel заставляет её ждать главный поток.
// Плохо: чтение и запись чередуются, раскладка считается на каждой итерации
items.forEach((el) => { el.style.height = el.offsetHeight + 10 + "px"; });

// Хорошо: сначала все чтения, потом все записи
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] + 10 + "px"; });

Почему macro по одной

Это отдельные внешние события. Между ними браузер получает шанс нарисовать кадр и обработать клик. Если бы очередь выполнялась целиком, страница зависала бы.

Почему micro все сразу

Это продолжение уже идущей работы. Пока цепочка .then не закончилась, ни клик, ни кадр не вклинятся и не увидят состояние наполовину. Цена: бесконечная цепочка microtasks заморозит страницу.

Правило для запоминания: macro приходит снаружи, micro доделывает начатое. В спецификации macro называется просто task.

Что является macrotask: клик или колбэк?

Клик только источник. Браузер создаёт macrotask, и уже в ней вызывается твой колбэк.

клик пользователя → браузер ставит задачу в очередь
задача → вызов колбэков click → стек пуст → microtasks

Правило: колбэк события или таймера выполняется внутри macrotask.

  • input: пользователь ввёл текст → задача → колбэк.
  • setTimeout: истёк таймер → задача → колбэк.

Исключение: button.click() из кода не создаёт задачу, колбэки вызываются сразу, в текущем стеке.

Как работают эти API

MessageChannel (macro)

Что это: канал связи из двух соединённых объектов-портов. Сообщение, отправленное в один порт, приходит в другой как macrotask.

Порты: это не сетевые порты вроде 8080. Номеров нет, выбирать нечего: браузер всегда создаёт ровно два порта, port1 и port2.

const { port1, port2 } = new MessageChannel();
port1.onmessage = (event) => console.log(event.data);
port2.postMessage("привет");   // придёт в port1 отдельной задачей

Две роли в коде:

  • port1.onmessage = fn — подписка. Сейчас fn не выполняется, браузер только запоминает её.
  • port2.postMessage("привет") — отправка. Сообщение уходит на port1.
port1.onmessage = fn          // подписались
port2.postMessage("привет")   // отправили
                              // текущий код дошёл до конца
macrotask → fn(event)         // сообщение доставлено, event.data === "привет"

Важно: fn не является задачей сама по себе. Задачу создаёт браузер при доставке сообщения, а fn выполняется внутри неё.

Вариант с addEventListener: подписка через него требует ещё вызова port1.start(). Присваивание onmessage запускает порт автоматически.

Разгружает ли MessageChannel тяжёлую работу? Сам по себе нет: это только канал связи. Разгрузка зависит от того, как он используется.

СпособГде идёт работаРезультат
Разбивка на куски (применение 1)главный потокобъём работы тот же, но браузер успевает рисовать между кусками
Web Worker (применение 2)отдельный потокглавный поток свободен всё время расчёта

Большие данные: сообщение копируется, и копирование большого объекта само занимает время в главном потоке. Для бинарных данных есть передача без копирования: ArrayBuffer указывают во втором аргументе, и он переходит получателю, а у отправителя становится пустым.

const buffer = new ArrayBuffer(100_000_000);
worker.postMessage({ buffer }, [buffer]);   // без копирования
console.log(buffer.byteLength);             // 0

Применение 1: разбить долгую работу на части, чтобы не пропускать кадры.

Задача. Обработка 100 000 строк занимает 200 мс. Одной задачей она пропустит 11 кадров, и страница зависнет.

Решение. Делим работу на куски примерно по 5 мс и запускаем каждый отдельной macrotask. Между ними браузер может нарисовать кадр и обработать клик.

[кусок 5 мс] [кусок 5 мс] [кусок 5 мс] кадр [кусок 5 мс] ...

Почему не setTimeout. Он тоже создаёт macrotask, но после нескольких вложенных вызовов браузер ждёт минимум 4 мс перед каждым следующим, даже при setTimeout(fn, 0). Работа простаивает:

СпособПауза перед куском40 кусков по 5 мс
setTimeout(fn, 0)минимум 4 мсоколо 360 мс
MessageChannelбез этого ограниченияоколо 200 мс

Как отмерить 5 мс и запустить следующую часть. Заранее длительность неизвестна, поэтому код обрабатывает строки по одной и после каждой смотрит на часы.

const { port1, port2 } = new MessageChannel();
const SLICE_MS = 5;
let index = 0;                                // место, где остановились

port1.onmessage = () => {
  const start = performance.now();            // начало куска

  while (index < rows.length) {
    processRow(rows[index]);
    index++;

    if (performance.now() - start >= SLICE_MS) break;  // 5 мс прошло, стоп
  }

  if (index < rows.length) {
    port2.postMessage(null);                  // ставим следующую macrotask
  }
};

port2.postMessage(null);                      // запускаем первый кусок

Пример разбивки: 1000 строк, за 5 мс успевается 300.

Кусокindex в началеОбработано строкindex в конце
10300300
2300300600
3600300900
4900100, строки кончились1000

Между кусками браузер может нарисовать кадр. index хранится снаружи функции, поэтому после её завершения место не теряется.

Что делает port2.postMessage(null):

  • Куда идёт сообщение: отправляем через port2, получает port1.
  • Откуда берётся macrotask: доставка сообщения и есть задача. Браузер ставит её в очередь, а она вызывает port1.onmessage.
  • Почему null: содержимое не важно. Сообщение служит только сигналом «запусти следующий кусок».
port2.postMessage(null) → браузер ставит задачу → port1.onmessage

Что происходит по шагам:

  1. port2.postMessage ставит macrotask в очередь.
  2. Она вызывает port1.onmessage, код запоминает время начала.
  3. Цикл обрабатывает строки, пока не пройдёт 5 мс.
  4. Если строки остались, код снова вызывает port2.postMessage. Номер строки хранится в index, поэтому следующий кусок продолжит с того же места.
  5. Задача заканчивается, стек пуст. Браузер может нарисовать кадр или обработать клик.
  6. Следующая macrotask продолжает работу с шага 2.

Ограничение: время проверяется только между строками. Если одна строка обрабатывается 30 мс, кусок займёт 30 мс, потому что прервать функцию посередине нельзя.

Время в таблице расчётное, без учёта отрисовки.

Применение 2: отдельный канал для каждого запроса к воркеру.

Задача. Воркер работает в своём потоке, поэтому тяжёлый расчёт не пропускает кадры. Но у него один общий onmessage. Если страница отправит два запроса, ответы придут в одно место, и без лишних id непонятно, какой ответ к какому запросу.

Решение. На каждый запрос создаём канал и передаём воркеру port2. Воркер отвечает в этот порт, поэтому ответ приходит только тому, кто спрашивал.

// main.js
const worker = new Worker("worker.js");

function calculate(numbers) {
  return new Promise((resolve) => {
    const { port1, port2 } = new MessageChannel();
    port1.onmessage = (event) => {
      resolve(event.data);
      port1.close();
    };
    worker.postMessage({ numbers }, [port2]);   // порт передаётся вторым аргументом
  });
}

const sum = await calculate(bigArray);   // интерфейс не зависает

// worker.js
self.onmessage = (event) => {
  const [replyPort] = event.ports;   // полученный port2
  const sum = event.data.numbers.reduce((a, b) => a + b, 0);
  replyPort.postMessage(sum);
};

Порядок работы:

  1. Страница создаёт канал и отправляет воркеру данные и port2.
  2. Воркер считает в своём потоке, главный поток свободен и рисует кадры.
  3. Воркер отправляет результат в port2.
  4. На странице появляется macrotask, port1.onmessage завершает промис.
  5. Код после await продолжается как microtask.

Применение 3: прямая связь двух воркеров. Страница передаёт по одному порту каждому воркеру, и дальше они обмениваются данными напрямую, не нагружая главный поток.

const { port1, port2 } = new MessageChannel();
parser.postMessage({ output: port1 }, [port1]);
renderer.postMessage({ input: port2 }, [port2]);

postMessage (macro)

Что это: метод отправки сообщения. Он есть у окна, воркера и порта. У получателя появляется macrotask, которая вызывает onmessage.

Данные: передаётся копия, а не ссылка на объект.

Применение: связь с iframe, вкладкой, открытым окном или воркером.

// Родительская страница
iframe.contentWindow.postMessage("привет", "https://widget.example");

// Внутри iframe
window.addEventListener("message", (event) => {
  if (event.origin !== "https://parent.example") return;   // проверка отправителя
  console.log(event.data);
});

Важно: при обмене между окнами указывай точный адрес получателя и проверяй event.origin, иначе сообщение может прочитать или подделать чужой сайт.

Остальные API

queueMicrotask (micro) ставит функцию в очередь microtasks. Она выполнится, когда опустеет стек.

queueMicrotask(() => console.log("2"));
console.log("1");   // вывод: 1, 2

queueMicrotask или requestAnimationFrame: что выбрать, чтобы код выполнился прямо перед перерисовкой?

queueMicrotaskrequestAnimationFrame
Когда выполнитсякак только опустеет стекпрямо перед отрисовкой
Привязка к кадрунетда
Для чегододелать работу до следующей задачиизменить DOM к ближайшему кадру
 
0 мс      macro → queueMicrotask(fn)
1 мс      fn выполнилась, до кадра ещё почти 16 мс
2 мс      следующие витки macro + micro

Правило: microtask выполнится раньше отрисовки, но не обязательно непосредственно перед ней. Для кода перед кадром нужен requestAnimationFrame.

Как измерить время от microtask до кадра:

queueMicrotask(() => {
  const start = performance.now();

  requestAnimationFrame(() => {
    console.log(`до кадра: ${performance.now() - start} мс`);
  });
});

Что показывает замер: сколько времени прошло между microtask и колбэком rAF.

Пустой стек не значит, что работы больше нет. queueMicrotask ставит функцию в очередь сразу, а выполняется она, когда стек опустел. Но в очередях ещё могут ждать другие задачи:

стек пуст → наша micro (замер начался)
          → другие micro из очереди
          → следующая macro, если кадр ещё не настал
          → её micro
          → rAF (замер закончился)

Чего он не показывает: простой. В этот промежуток могли выполняться другие macro и micro, поэтому 12 мс в замере не значат 12 мс простоя. Отрисовка начинается уже после колбэков rAF, поэтому её старт замер тоже точно не ловит.

Как увидеть настоящую картину: вкладка Performance в DevTools показывает все задачи, отрисовку и свободные промежутки на одной шкале.

MutationObserver (micro) следит за изменениями DOM. Изменения копятся, и колбэк вызывается один раз со всем списком, а не на каждое изменение.

const observer = new MutationObserver((records) => console.log(records.length));
observer.observe(el, { childList: true });
el.append(a);
el.append(b);   // один вызов, в списке 2 записи

Колбэк rAF (шаг 3) не macro и не micro. requestAnimationFrame кладёт функцию в отдельный список, браузер выполняет его прямо перед отрисовкой. Колбэк срабатывает один раз и получает время кадра.

requestAnimationFrame((time) => {
  el.style.transform = `translateX(${time / 10}px)`;
});

Как разбивают работу сегодня

В браузерах с поддержкой есть готовый API, а MessageChannel остаётся запасным вариантом:

for (const chunk of chunks) {
  processChunk(chunk);
  await scheduler.yield();   // уступить браузеру и продолжить
}

Перед использованием проверяй поддержку: "scheduler" in window && "yield" in scheduler. Задачи длиннее 50 мс считаются long task и ухудшают метрику INP.

Проверь порядок сама

console.log("1 синхронно");
setTimeout(() => console.log("macro: setTimeout"));
requestAnimationFrame(() => console.log("rAF"));
Promise.resolve().then(() => console.log("micro: then"));
console.log("2 синхронно");

Нажми «Запустить», код выполнится здесь по-настоящему.

Первые три строки идут всегда в порядке: 1, 2, micro. А вот setTimeout и rAF могут поменяться местами: всё зависит от того, сколько осталось до кадра.

React: как работает внутри

React Scheduler

Джуну: Scheduler — диспетчер React. Он не даёт React занять браузер надолго: поработал немного, уступил, продолжил.

Планировщик режет работу React на короткие macrotasks, чтобы браузер успевал рисовать кадры.

Как устроен

  • Очередь: задачи лежат в очереди с приоритетами (min-heap). Первой берётся задача с самым ранним дедлайном.
  • Запуск: port.postMessage ставит macrotask, а обработчик onmessage выполняет задачи из очереди.
  • Бюджет: работа идёт кусками примерно по 5 мс, а не на весь кадр в 16,6 мс. Остаток кадра нужен браузеру.
  • Прерывание: время истекло, значит React останавливается и ставит продолжение новой macrotask.
postMessage → macrotask → работа 5 мс → время вышло?
  да  → postMessage (браузер может нарисовать кадр)
  нет → следующий компонент

Ограничение: прервать можно только между компонентами. Один компонент на 100 мс всё равно заблокирует кадр.

Мидлу: что это даёт на практике

  • Несрочный рендер большого списка не блокирует ввод.
  • Срочное обновление может прервать незавершённый несрочный рендер, и тот начнётся заново.
  • Поэтому компонент может отрендериться, но не попасть на экран. Побочным эффектам в рендере не место.

Сеньору: Lanes и выбор API

Lanes — приоритеты обновлений внутри React в виде битовой маски. Lanes решают, что важнее, а Scheduler решает, когда запускать работу и когда уступить браузеру.

Фазы Render и Commit

Джуну: сначала React думает, что должно измениться (Render), потом меняет страницу (Commit). Вызов компонента ещё не значит изменение DOM.

RenderCommit
Что делаетвызывает компоненты и вычисляет изменениязаписывает изменения в DOM

Порядок эффектов:

  1. React записывает изменения в DOM.
  2. useLayoutEffect выполняется синхронно, до отрисовки.
  3. Браузер рисует кадр.
  4. useEffect обычно выполняется после отрисовки.

Мидлу: порядок и очистка эффектов

useEffect(() => {
  const id = setInterval(tick, 1000);

  return () => clearInterval(id);   // очистка перед следующим запуском и при удалении
}, []);
  • Automatic Batching: несколько setState подряд дают один рендер.
  • useLayoutEffect: нужен, когда надо измерить DOM и изменить его до показа. Он блокирует отрисовку, поэтому должен быть быстрым.

Сеньору: Fiber

Fiber — узел дерева с данными о компоненте и незавершённой работе. React строит дерево work-in-progress и в Commit подменяет им текущее. Поэтому незавершённый Render можно выбросить, и пользователь не увидит промежуточное состояние.

Reconciliation: сравнение деревьев

React сравнивает новое дерево с предыдущим и меняет в DOM только отличия.

Что запускает рендер

  • изменение состояния (useState, useReducer);
  • изменение контекста, на который подписан компонент;
  • рендер родителя: дочерние компоненты рендерятся, даже если их пропсы не изменились, пока их не защитит memo;
  • forceUpdate в классовых компонентах и Fast Refresh в разработке.

StrictMode не запускает обновления. В разработке он только вызывает рендер дважды, чтобы найти побочные эффекты.

Правила сравнения

Почему индекс нельзя использовать как key

При вставке в начало индексы сдвигаются. React считает, что элементы на месте, и оставляет состояние на прежней позиции, поэтому оно оказывается у другой записи.

До:    key=0 "Анна"  <input value="заметка Анны">
Вставили "Борис" в начало
После: key=0 "Борис" <input value="заметка Анны">   // чужая заметка
       key=1 "Анна"  <input value="">

Правило: используй стабильный уникальный key из данных, например id записи. Индекс допустим, только если список не меняет порядок и у элементов нет состояния.

Мидлу: лишние рендеры и сброс состояния

const Row = memo(function Row({ item, onSelect }) { /* ... */ });

// Новая функция на каждый рендер ломает memo
<Row item={item} onSelect={() => select(item.id)} />

// Стабильная ссылка
const onSelect = useCallback((id) => select(id), [select]);
<Row item={item} onSelect={onSelect} />

Сброс состояния через key: смена key создаёт компонент заново. Это простой способ очистить форму при смене пользователя:

<ProfileForm key={user.id} user={user} />

Сеньору: почему сравнение быстрое

Точное сравнение двух деревьев слишком дорого. React использует эвристику O(n): разный тип значит другое поддерево, а key помогает сопоставить элементы списка. Перенос компонента на другой уровень дерева теряет его состояние, даже если тип тот же.

useTransition, useDeferredValue, Suspense

useTransition

Помечает обновление как несрочное. Старый экран остаётся отзывчивым, новый готовится в фоне, isPending показывает, что идёт переход.

const [isPending, startTransition] = useTransition();

startTransition(() => setTab("archive"));

useDeferredValue

Создаёт отстающую копию значения. Поле ввода обновляется сразу, а тяжёлый список догоняет его несрочным рендером.

const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);

<input value={query} onChange={(e) => setQuery(e.target.value)} />
<Results query={deferredQuery} />

useTransitionвызов обновления состоянияесть доступ к setState
useDeferredValueзначениезначение приходит извне, например из пропсов

Suspense

Показывает fallback, пока часть дерева не готова: не загружен код или данные. Работает с React.lazy, use и библиотеками с поддержкой Suspense.

<Suspense fallback={<Spinner />}>
  <Comments />
</Suspense>

useTransition подробнее

Джуну: «обнови это, когда будет время, но не мешай пользователю». Быстрее работа не становится, зато интерфейс не зависает.

Мидлу: что важно помнить

  • Suspense: в транзишне старый контент остаётся на экране, а не сменяется на fallback.
  • Поле ввода: значение input должно обновляться срочно. В транзишн оборачивай только фильтрацию.
  • Загрузка данных: транзишн сам ничего не загружает.
  • Асинхронные действия: isPending остаётся true до завершения функции. Обновления состояния после await нужно снова оборачивать.
startTransition(async () => {
  await saveEvent(data);

  startTransition(() => setSaved(true));   // после await оборачиваем снова
});

Сеньору: React прерывается только между компонентами, поэтому тяжёлый синхронный код внутри одного компонента транзишн не спасёт. Такую работу разбивают на куски или выносят в Web Worker. Начиная с React 19.3 транзишны рендерятся независимо, и медленный не задерживает быстрый.

Hydration

React подключает интерактивность к HTML, который уже пришёл с сервера.

  1. Сервер рендерит HTML и отправляет его: контент виден до загрузки JS.
  2. Браузер загружает JS.
  3. hydrateRoot рендерит те же компоненты и сравнивает результат с готовым DOM.
  4. React подключает обработчики событий и состояние, DOM при этом не пересоздаётся.

Ошибка hydration: результат на клиенте отличается от серверного HTML. Частые причины: Date.now(), Math.random(), чтение window во время рендера.

Мидлу: как избежать ошибки

// Плохо: сервер и браузер дадут разный результат
<span>{new Date().toLocaleTimeString()}</span>

// Хорошо: значение только для браузера появляется после монтирования
const [time, setTime] = useState(null);
useEffect(() => setTime(new Date().toLocaleTimeString()), []);

Сеньору: стоимость и частичная гидрация

  • Цена: до конца hydration страница видна, но клики могут не работать. Тяжёлая гидрация ухудшает INP.
  • Selective Hydration: части внутри Suspense гидрируются отдельно, и React гидрирует раньше ту, по которой кликнули.
  • Server Components: их код не попадает в браузер и не гидрируется, поэтому JS становится меньше.

Как работает revalidate в ISR

Страница не обновляется сама каждые n секунд. Обновление запускает запрос:

  1. Пока не прошло n секунд, все получают версию из кэша.
  2. После этого первый запрос тоже получает старую версию и запускает генерацию в фоне.
  3. Когда генерация закончена, следующие запросы получают новую страницу.

Джуну: как выбрать

  1. Страница одинакова для всех и редко меняется? Static.
  2. Одинакова для всех, но обновляется? ISR.
  3. Зависит от пользователя или запроса? SSR.
  4. Закрытый интерфейс, поисковики не важны? Подойдёт и CSR.

Сеньору: на что смотреть

  • Динамика: чтение cookies() или headers() делает маршрут динамическим, и он теряет статический кэш.
  • Prefetch: ссылки создают запросы к серверу, на больших списках это заметная нагрузка.
  • Граница 'use client': чем ниже по дереву, тем меньше JS в браузере.
  • ISR: при нескольких серверах кэш нужно делать общим, иначе экземпляры отдадут разные версии.

  • next/root-params: чтение [lang] из любого Server Component.
  • Instant Navigations: Partial Prefetching и инструменты DevTools, включаются флагами.

Promise: комбинаторы

Джуну: промис — обещание результата в будущем. Он бывает в трёх состояниях: pending, fulfilled и rejected. Его колбэки .then выполняются как microtasks.

const promise = new Promise((resolve, reject) => reject(error));

Promise.raceпри первом завершении, любомзначение первогоошибка первого, если он упал

await Promise.allSettled([ok, fail]);
// [{ status: "fulfilled", value: 1 }, { status: "rejected", reason: error }]

Что выбрать

  • Нужны все результаты: all.
  • Нужны все, даже если часть упала: allSettled.
  • Таймаут запроса: race.
  • Первое успешное зеркало: any.

Мидлу: типичные приёмы

// Таймаут запроса
const timeout = new Promise((_, reject) =>
  setTimeout(() => reject(new Error("timeout")), 5000),
);
const data = await Promise.race([fetch(url), timeout]);

// Обработка каждого результата
const results = await Promise.allSettled(requests);
const ok = results.filter((r) => r.status === "fulfilled").map((r) => r.value);

Сеньору: подводные камни

  • Отмены нет: all и race не останавливают остальные промисы. Запросы отменяет AbortController.
  • Параллельность: Promise.all на 1000 запросов запустит их сразу. Ограничивай их число пулом.
  • Без обработки ошибки: отклонённый промис без обработчика вызывает unhandledrejection.
  • Последовательно или параллельно: await в цикле идёт по одному, map с Promise.all запускает всё сразу.
const controller = new AbortController();
fetch(url, { signal: controller.signal });
controller.abort();

WebSocket

Постоянное двустороннее соединение: сервер может отправлять данные сам, без запроса клиента.

Сервер (пакет ws)

import { WebSocketServer } from "ws";

const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (ws) => {
  ws.send("hello");

  ws.on("message", (message) => {
    console.log(message.toString());   // по умолчанию приходит Buffer
  });
});

Клиент (браузер)

const socket = new WebSocket("ws://localhost:8080");

socket.onopen = () => socket.send(inputValue);   // отправлять можно после открытия
socket.onmessage = (event) => console.log(event.data);

На реальном сайте используй wss://. Каждое входящее сообщение обрабатывается в браузере как macrotask.

Мидлу: когда что выбрать

ТехнологияНаправлениеПодходит для

Сеньору: что нужно в продакшене

  • Переподключение: соединение обрывается, нужен повтор с растущей задержкой.
  • Heartbeat: ping и pong помогают обнаружить зависшее соединение.
  • Авторизация: браузерный API не умеет задавать произвольные заголовки, обычно используют cookie или токен первым сообщением.
  • Пропущенные сообщения: после переподключения их нужно догрузить, например по последнему id.
  • Масштабирование: при нескольких серверах сообщения между ними передают через брокер.
function connect(attempt = 0) {
  const socket = new WebSocket(url);

  socket.onopen = () => { attempt = 0; };
  socket.onclose = () => {
    const delay = Math.min(1000 * 2 ** attempt, 30000);
    setTimeout(() => connect(attempt + 1), delay);
  };
}

Throttle и debounce

ThrottleDebounce
Правилоне чаще раза в N мсчерез N мс после последнего вызова
Примерscroll, resizeпоиск при вводе
 
function throttle(func, limit) {
  let lastCall = 0;

  return (...args) => {
    const now = Date.now();

    if (now - lastCall >= limit) {
      lastCall = now;
      func(...args);
    }
  };
}

function debounce(func, delay) {
  let timer;

  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => func(...args), delay);
  };
}

Этот throttle выполняет первый вызов сразу, а вызовы внутри интервала отбрасывает, включая последний.

Джуну: как запомнить

  • Throttle: лифт уходит раз в минуту, сколько бы людей ни пришло.
  • Debounce: лифт ждёт, пока люди перестанут заходить.

Мидлу: ошибка в React

// Плохо: новый debounce на каждый рендер, таймер теряется
const onChange = debounce(search, 300);

// Хорошо: один экземпляр на компонент
const onChange = useMemo(() => debounce(search, 300), [search]);

Сеньору: последний вызов и отмена

В анимациях прокрутки вместо throttle часто берут rAF: не больше одного обновления на кадр. Debounce поиска должен отменять и таймер при размонтировании, и устаревший запрос через AbortController, иначе старый ответ может перезаписать новый.

function rafThrottle(func) {
  let scheduled = false;

  return (...args) => {
    if (scheduled) return;
    scheduled = true;
    requestAnimationFrame(() => {
      scheduled = false;
      func(...args);
    });
  };
}

Задача: поворот массива без копирования

Массив не меняется: хранится только счётчик сдвига, а индекс вычисляется при чтении, поэтому rotate работает за O(1).

const getRotatableArr = (arr) => {
  let rotateCount = 0;

  return {
    rotate(direction = 1, step = 1) {
      rotateCount += direction * step;
    },

    get(i) {
      const originalIndex = (i - (rotateCount % arr.length) + arr.length) % arr.length;

      return arr[originalIndex];
    },
  };
};

const rotatable = getRotatableArr(["a", "b", "c"]);
rotatable.rotate();   // вправо на 1: c, a, b
rotatable.get(0);     // "c"

function createStore(state) {
  const listeners = new Set();

  return {
    getState: () => state,
    setState(next) {
      state = next;
      listeners.forEach((listener) => listener(state));
    },
    subscribe(listener) {
      listeners.add(listener);

      return () => listeners.delete(listener);
    },
  };
}
